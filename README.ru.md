# TaskClosureKit

[English](README.md) · [Русский](README.ru.md)

TaskClosureKit — локальный инструмент командной строки для инженеров и AI coding agents.
Он проверяет, соответствует ли инженерная задача согласованным критериям приёмки.
Он сохраняет доказательства и позволяет оператору закрыть задачу.

Начните с этой команды:

```sh
npx taskclosurekit --help
```

При первом запуске npm может запросить разрешение на загрузку пакета.
Клонировать Git-репозиторий не нужно.

## Требования

- Node **22 или новее** и npm/npx.
- Python **3.9 или новее**.
- macOS или Linux с POSIX API ограничения ресурсов.
- Системный Git в `/usr/bin` или `/bin`.

Windows не поддерживается.
Локальные проверки выполнены на macOS с Python 3.9.6, Node 22.23.1 и npm 10.9.8.
Подтверждённой матрицы проверок Linux и других версий здесь нет.

Launcher использует первый существующий Python: `/usr/bin/python3`, затем `/bin/python3`.
Для другого установленного Python задайте `TASKCLOSUREKIT_PYTHON` с абсолютным путём исполняемого файла.
Пакет не имеет сторонних зависимостей и install scripts.
Он не устанавливает Python и не мигрирует существующие stores.

## Как закрывается задача

**Контракт** задаёт репозиторий, разрешённые чтения и записи, проверки, критерии приёмки и требования к review.
**Store** хранит журнал задачи и его локальный HMAC-ключ.
Результат каждой проверки относится к конкретному контракту, состоянию репозитория и среде исполнения.
Изменения могут сделать прежний `PASS` устаревшим.

```text
create → authorize → baseline → implement and stage → check
       → evaluate → review → evaluate → CLAIMABLE → close → CLOSED
```

`CLAIMABLE` означает, что актуальные доказательства допускают утверждение о завершении.
`CLOSED` означает, что оператор зафиксировал это утверждение отдельным действием `close`.
Тип утверждения — `configured-acceptance-satisfied`.
Оно охватывает настроенные критерии для одного состояния задачи.
Оно не доказывает полную корректность или готовность к production.

## Запустите первую задачу

### 1. Подготовьте контракт

Откройте [пример контракта](examples/contract-v2.json).
Сохраните его JSON в файл вне целевого репозитория.
Укажите в `repository` абсолютный физический путь своего репозитория.
Задайте ID задачи и разрешённые пути файлов для своей задачи.
Перед использованием изучите весь контракт.

Пример разрешает изменения в `src/foo.py` и требует неизменяемый источник `README.md`.
Его проверка `git-index-whitespace-v1` проверяет только пробельные ошибки в staged-изменениях.
Она не проверяет поведение программы.
Для тестов или сборки используйте проверенную [конфигурацию пресетов](examples/presets-engineering-v21.json).
См. [инженерный контракт](examples/contract-engineering-v21.json) и [справочник CLI](docs/CLI.md#real-engineering-checks).

Целевой репозиторий должен иметь исходный commit и обычный каталог `.git` с отдельными SHA-1 objects.
Packed objects, alternates и linked worktrees не поддерживаются.
Поэтому обычный клонированный репозиторий может оказаться неподдерживаемым.
Другие ограничения Git описаны в [границах безопасности](docs/SAFETY_BOUNDARIES.md#git).

Используйте абсолютные физические пути для контракта и store.
Держите оба вне целевого репозитория.
Держите контракт вне store.
Каталог store не должен существовать до `task create`.
Symlink aliases не поддерживаются.

### 2. Создайте и разрешите задачу

Замените пути в примере своими путями.
Сохраните переменные в том же терминале для следующих шагов.
Запускайте каждую команду отдельно в интерактивном терминале.

```sh
TASK_STORE=/absolute/path/to/new-store
TASK_CONTRACT=/absolute/path/to/contract.json
npx taskclosurekit --store "$TASK_STORE" task create "$TASK_CONTRACT" --json
npx taskclosurekit --store "$TASK_STORE" authorize --json
npx taskclosurekit --store "$TASK_STORE" baseline --json
```

Перед подтверждением изучите контракт.
Для `authorize` введите точный digest действия, показанный в терминале.
`review --human` и `close` требуют отдельных подтверждений оператора.
JSON-вывод и piped input не заменяют эти подтверждения.
Утверждение агента не заменяет решение оператора.

### 3. Внесите и проверьте изменение

Меняйте только разрешённые файлы.
Добавьте изменения в Git index.
Запустите проверку из примера контракта:

```sh
npx taskclosurekit --store "$TASK_STORE" check git-index-whitespace-v1 --json
npx taskclosurekit --store "$TASK_STORE" evaluate --json
```

Успешная проверка сохраняет `PASS`.
До review оценка возвращает `NOT_CLAIMABLE`, причину `missing_trusted_review` и exit code **1**.
Это ожидаемый результат.

### 4. Проведите review и закройте задачу

Изучите staged diff в целевом репозитории.
Запускайте каждую команду отдельно.
Подтверждайте review только после изучения текущих изменений и доказательств.

```sh
npx taskclosurekit --store "$TASK_STORE" review --human --json
npx taskclosurekit --store "$TASK_STORE" evaluate --json
npx taskclosurekit --store "$TASK_STORE" close --json
npx taskclosurekit --store "$TASK_STORE" status --next --json
```

Если оценка возвращает `CLAIMABLE`, подтвердите отдельное действие `close`.
Успешное закрытие сохраняет `CLOSED`.
`status --next --json` показывает актуальные доказательства, блокирующие причины и следующее разрешённое действие.
Команда восстанавливает состояние задачи для другого процесса без истории чата.

До закрытия повторяйте затронутые проверки после правок.
Затем повторите review для текущего состояния.
После закрытия используйте новую задачу для нового состояния.
При изменении полномочий создайте новую согласованную задачу и store.
Обновление программы тоже может сделать прежние доказательства неактуальными.
Для фиксированной версии пакета используйте `npx taskclosurekit@2.1.1` вместо `npx taskclosurekit` на протяжении задачи.

## Доверие и приватность

- Проверки scope не создают изоляцию ОС и не предотвращают доступ к файлам хоста.
- Терминальные подтверждения предполагают локального оператора. Они не удостоверяют личность человека или независимость reviewer.
- Обязательная независимость reviewer блокирует claim без доверенного доказательства. Импортированные review и assertions сохраняют agent-attested trust.
- Локальные HMAC-записи выявляют поддержанные нарушения целостности. Процесс с равными правами на хосте может заменить инструмент, ключ и журнал вместе.
- Исполнение проверок ограничено по времени, объёму вывода и POSIX resource limits. Ограничение адресного пространства действует только на Linux.
- Инструмент отбрасывает сырой вывод проверок. Журнал всё равно содержит метаданные задачи и снимки.

Не помещайте credentials, исходные `.env` или персональные данные во входы задачи или доказательства.
У инструмента нет сетевого CI adapter, SDK, completion hook или deployment service.
Его тестовый CI adapter не подтверждает результаты реального CI provider.
См. [границы продукта](docs/PRODUCT_BOUNDARIES.md) и [границы безопасности](docs/SAFETY_BOUNDARIES.md).

## Данные задач и удаление

Удаление инструмента не удаляет stores, внешние входы или целевой репозиторий.
Перед удалением решите, какие доказательства задачи нужно сохранить.
Сохраните полный приватный store, включая ключ, вместе с относящимися к нему внешними входами.

Для восстановления также нужны исходные пути, состояние репозитория и идентичность исполняемого кода.
Один архив не гарантирует восстановления.
Удаление журнала или ключа лишает возможности проверяемого восстановления.

Удаляйте только конкретные файлы и каталоги, которые решили больше не хранить.
npm управляет своим кешем отдельно.
См. [совместимость и обновления](docs/COMPATIBILITY.md).
